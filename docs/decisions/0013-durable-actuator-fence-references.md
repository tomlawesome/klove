# ADR 0013: accept durable cross-service actuator-fence references

Status: accepted

Date: 2026-08-21

## Context

Klove has one cancellation-safe, in-process `PrinterAdmissionGates` lock per
canonical printer UUID, but the evidence consulted under that lock is split
across services. Print-start ambiguity is authoritative in `StartJournal`.
Coordinator progress and ambiguity are authoritative in `DispatchJournal`.
Job-control tasks, idempotency results, and uncertain state tokens exist only
in the current `ControlService` process. `CompositeActuatorFenceInspector`
checks control memory and the start journal, but not the coordinator journal.

That arrangement serializes live calls but cannot prove a complete fence after
a process crash, a mixed restore, or an independently committed store update.
It can also let a lifecycle mutation observe a false-clear gap between an
actuator deciding to proceed and its owner journal committing an unresolved
row. Issue #112 requires one durable cross-service contract before registry
schema, recovery tooling, or runtime behaviour changes.

The exact current inventory is:

| Boundary | Current authority and restart semantics | Primary evidence |
| --- | --- | --- |
| shared admission | `PrinterAdmissionGates` is an in-memory lock/lease map; restart recreates it empty | `src/klove/orchestration/admission.py`, `tests/unit/test_admission.py` |
| lifecycle proof | `CompositeActuatorFenceInspector` asks only control memory and `StartJournal`; the lifecycle service holds the shared gate across proof, registry commit, and runtime handoff | `src/klove/orchestration/onboarding.py`, `tests/unit/test_onboarding_service.py` |
| job control | `ControlService._journal` and `_uncertain_tokens` own in-flight and `outcome_unknown` evidence only for the process epoch; restart discards both and boot-scoped tokens reject replay | `src/klove/orchestration/control.py`, `tests/unit/test_control_service.py` |
| print start | `StartJournal.start_operations` durably owns `dispatching`, `confirmed`, and `outcome_unknown`; startup/reconnect reads unresolved rows and never retries the RPC | `src/klove/persistence/start_journal.py`, `src/klove/orchestration/start.py`, `tests/unit/test_start_journal.py`, `tests/unit/test_start_service.py` |
| coordinator | `DispatchJournal.dispatch_operations` durably owns the complete coordinator state machine and the spool retains exact accepted bytes; startup recovers or reconciles before readiness | `src/klove/persistence/dispatch_journal.py`, `src/klove/orchestration/dispatch.py`, `tests/unit/test_dispatch_coordinator.py` |
| production composition | `serve()` composes lifecycle, control, registry, and the start-journal fence check; it does not add coordinator state to that composite proof | `src/klove/app.py`, `tests/unit/test_api.py`, `tests/unit/test_bootstrap.py` |

The coordinator omission means a durable `uploading`, `starting`, `printing`,
or `outcome_unknown` row can be invisible to a lifecycle mutation. The
process-only control journal means a crash can erase its only unresolved-fence
record. These are the two false-clear cases this decision removes.

## Decision

### Authority and identity

The canonical registry database will own a durable actuator-fence catalogue.
The catalogue is an admission index, not a second outcome journal. Each
reference contains only:

- an opaque canonical UUIDv4 `fence_reference_id` generated by the catalogue;
- the exact canonical printer UUID;
- one closed `fence_kind`: `control`, `print_start`, or `coordinator`;
- one closed `owner_store`: `control_journal`, `start_journal`, or
  `dispatch_journal`;
- the owner's immutable UUIDv4 `store_id`, positive schema version, and exact
  canonical UUIDv4 operation identity;
- one catalogue state: `prepared`, `active`, or `resolved`;
- bounded integer creation and transition times and a closed resolution code.

The tuple `(owner_store, store_id, owner_schema_version, operation_id,
fence_kind)` is unique. A reference never contains a credential, endpoint,
request body, archive or G-code data, filename, state token, job details,
remote response, or exception text. Those remain in their owning store where
required by the accepted operation contract.

Every registry and owner store has one immutable installation UUID and one
immutable store UUID in validated metadata. A fence reference is compatible
only with its exact installation, named store UUID, and an explicitly accepted
owner schema version. Equality of paths, filenames, copied database contents,
or near schema versions is never compatibility evidence.

Catalogue rows are never deleted or reused. State transitions use an exact
optimistic predecessor and append an immutable transition event in the same
registry transaction. `resolved` is terminal. The catalogue exposes internal
queries only: one canonical printer UUID, an exclusive sequence cursor, and a
limit from 1 through 1,000 in stable ascending order. No northbound route is
added.

### Owner states

The owner journal remains authoritative for whether an operation may have
acted. The catalogue projection and admission effect are:

| Kind | Owner state | Catalogue/admission meaning |
| --- | --- | --- |
| control | no owner row after `prepared` | conservative fence until startup proves the reservation never committed |
| control | `dispatching` | unresolved; the RPC may occur or may have occurred |
| control | `outcome_unknown` | unresolved across restart and every idempotency key |
| control | `confirmed` or `denied_before_dispatch` | terminal owner evidence; catalogue may resolve |
| print start | no owner row after `prepared` | conservative fence until startup proves the reservation never committed |
| print start | `dispatching` | unresolved; the one start RPC may have occurred |
| print start | `outcome_unknown` | unresolved across restart and every key |
| print start | `confirmed` | terminal owner evidence; catalogue may resolve |
| coordinator | `receiving`, `accepted`, `uploading`, `verified`, or `starting` | active pipeline; lifecycle and competing actuation remain fenced |
| coordinator | `printing` | active known print; lifecycle and another print remain fenced; exact bound job control may proceed |
| coordinator | `outcome_unknown` | unresolved and fences every actuator and lifecycle mutation |
| coordinator | `completed`, `cancelled`, or `failed` | terminal owner evidence; catalogue may resolve |

The control owner becomes a new private SQLite/WAL journal. It durably records
the operation identity, printer UUID, idempotency key, operation, caller state
token, and the bounded immutable job/preflight evidence needed for read-only
reconciliation. It commits `dispatching` before the parameter-free RPC.
Transport or internal ambiguity becomes durable `outcome_unknown`; no action
is retried. Later exact changed control evidence may terminally supersede the
old token, and exact postcondition evidence may confirm it. A process restart
alone is not resolution evidence. This deliberately strengthens ADR 0001's
process-epoch journal while retaining its boot-scoped replay denial.

### Admission and conflict rules

`PrinterAdmissionGates` remains the sole live serialization primitive. Every
lifecycle mutation and every new control, direct print-start, or coordinator
operation holds the exact printer gate while consulting and changing fence
state. The catalogue applies these conflicts:

- lifecycle update, credential rotation, disable, and remove require zero
  non-resolved references of every kind;
- a new coordinator or direct print start requires zero non-resolved
  references, except exact references carried by its current composed chain;
- a control requires no unresolved control or print-start reference and no
  coordinator reference except `printing` for the exact confirmed job bound by
  the intent;
- a coordinator child stage may use only an explicit, unforgeable live lease
  naming its exact coordinator reference and any child print-start reference;
  it cannot ignore another operation's reference;
- a prepared, unknown, missing, corrupt, incompatible, or contradictory state
  always conflicts. There is no generic override.

Reference creation and terminal resolution belong to the service that owns the
operation. Registry and operator paths may inspect references but can never
resolve them. No manual clear, deletion, expiry, timeout, retention policy, or
capacity eviction is accepted. Exhaustion denies new work.

### Commit protocol and crash points

Creation uses this order under the shared printer gate:

1. Validate current evidence and prove no conflicting reference.
2. Commit a `prepared` catalogue reference.
3. Commit the owner's pre-dispatch row.
4. Transition the exact reference to `active`.
5. Recheck current evidence required by that actuator and dispatch at most
   once.

An owner may not perform a network action before step 3. An `active` transition
may not occur without reading back the exact owner row. Failure after step 2
leaves a conservative catalogue fence. Failure after step 3 leaves both owner
and catalogue evidence unresolved even when step 4 did not commit. No ordering
allows an owner row or network action to exist while the catalogue is clear.

Resolution uses the reverse conservative order:

1. Reconcile by reads only while holding the printer gate.
2. Commit a terminal state in the authoritative owner journal.
3. Read back that exact terminal row.
4. Transition the matching catalogue reference to `resolved` with a closed
   reason.

A crash before step 2 retains both fences. A crash between steps 2 and 4
retains a false-positive catalogue fence, which startup may resolve from the
terminal owner row. Catalogue resolution never precedes owner termination, so
there is no false-clear interval.

| Crash boundary | Durable evidence after restart | Required action |
| --- | --- | --- |
| before catalogue prepare | no reference and no owner row | no operation existed |
| after prepare, before owner reserve | `prepared`, owner absent | resolve as `never_dispatched` only during closed startup reconciliation |
| after owner reserve, before activation | `prepared` plus unresolved owner | promote to `active`; reconcile by reads only |
| after activation, before network call | `active` plus unresolved owner | treat as possibly dispatched; never retry |
| during or after network call | `active` plus unresolved owner | reconcile by reads only; ambiguity remains fenced |
| after owner terminal commit | active/prepared reference plus terminal owner | resolve the exact reference |
| after catalogue resolution | terminal owner plus resolved reference | accept only if all identities and states agree |

### Startup, reconnect, migration, and recovery

All actuator and lifecycle admission starts closed. Initialization validates
the registry, every owner schema, installation/store identities, catalogue
uniqueness, and the complete cross-store relation before activating a printer.
For each exact printer, reconciliation then:

1. pages through its non-resolved references within fixed bounds;
2. opens only the named compatible owner store and reads the exact operation;
3. resolves a `prepared` reference with no owner row only as
   `never_dispatched` because the accepted commit order proves no network call
   was permitted;
4. promotes a prepared reference whose exact unresolved owner row exists;
5. resolves a reference only from the exact terminal owner row;
6. retains unresolved owner evidence and performs only the already accepted
   bounded read-only reconciliation;
7. refuses readiness for a missing owner store, missing reference for an owner
   row, active orphan, duplicate, identity mismatch, invalid transition,
   contradiction, corrupt row, or unsupported past/future schema.

Reconnect repeats the affected owner's read-only reconciliation under the same
gate and never changes reference compatibility. A corrupt shared schema or
unavailable required store closes global readiness. A valid contradiction
that is provably confined to one canonical printer closes only that printer;
it cannot enumerate, block, or mutate another printer's rows.

The implementation migration is exclusive and contiguous. It adds catalogue
metadata and references for every non-terminal start and coordinator row before
the new runtime can open admission, and introduces the empty durable control
journal only after the old process is quiesced. Upgrade must prove the old
process has no in-flight control task; otherwise it aborts and leaves the old
state untouched. It never fabricates terminal evidence. Downgrade is
unsupported, and an older binary rejects the new registry and journal schemas.

A recoverable set is one quiesced registry snapshot (including the catalogue
and its transition history), the complete secret directory and HMAC key, the
control, start, and coordinator journals, and the complete dispatch spool.
The later backup slice must add a secret-free manifest with one fresh recovery
set UUID, the installation UUID, every store UUID/schema version, and an exact
digest for every member. Restore admits no subset and rejects mixed recovery
set IDs, rolled-back catalogues, omitted or extra stores, digest mismatch,
orphaned spool content, and any catalogue/owner disagreement. Restore and
migration never clear an unresolved outcome.

### Required implementation tests

The follow-on implementation must provide positive and negative tests for:

- every state and conflict-table row, including exact coordinator-printing job
  control and denial for a different job;
- every creation and resolution crash boundary above, with restart after each
  committed write and proof of no second dispatch;
- durable control ambiguity across process restart, changed-token read-only
  resolution, idempotency collision, capacity exhaustion, and journal failure;
- missing, orphaned, duplicate, stale, rolled-back, future-version, corrupt,
  cross-installation, wrong-store, wrong-operation, and contradictory
  references;
- lifecycle update, both rotations, disable, and remove racing each actuator
  stage without a false-clear observation;
- composed coordinator/start leases that admit only their exact chain and
  reject reuse, inheritance, cross-task, cross-printer, and stale leases;
- exact migration backfill and rollback from the immutable version-2 registry
  fixture plus existing version-1 migration coverage;
- stable bounded per-printer paging, no cross-printer enumeration, no
  unbounded labels or hostile material, and one printer's valid contradiction
  not mutating another;
- complete recovery-manifest mismatch and partial-set denial in the later
  backup/restore slice.

Security-sensitive authentication, authorization, control, decoding,
translation, and policy paths retain 100% statement and branch coverage. The
native Moonraker integration lane must prove a lost control response and a lost
start response remain fenced across a Klove restart without a second RPC.

## Consequences

- Lifecycle and actuation share one crash-safe source of admission truth while
  outcome authority remains in the narrow owning journals.
- Job-control ambiguity becomes durable; a restart no longer clears it merely
  by changing process epoch.
- Conservative orphan references can delay work but cannot create a
  false-clear gap. Only automatic proof from accepted ordering and exact owner
  evidence resolves them.
- The registry advances to a new schema and control gains a journal in the
  follow-on slice. Backup/restore commands, circuit breaking, observability,
  retention, and UI/API surfaces remain excluded.
