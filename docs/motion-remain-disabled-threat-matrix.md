# Motion remain-disabled threat matrix

This is the issue #134 audit requested by issue #19. It is evidence for a
later decision, not an architecture decision or an authorization to implement
an actuator. Homing, jogging, and extrusion remain disabled.

## Boundary and evidence snapshot

Moonraker exposes a generic G-code script method, while Klipper documents that
scripts may queue behind earlier G-code and that motion depends on mutable
G-code parsing state. A homing command may also be replaced by an
operator-defined homing override. Therefore neither arbitrary caller G-code nor
an arbitrary configured macro can cross Klove's boundary: either can select a
different actuator, alter persistent or modal state, expand into unreviewed
commands, or create effects that the caller-visible request does not bound.
Names and command availability prove only registration, not semantics.

Current Klove is narrower:

- `ControlOperation` contains only pause, resume, and cancel. The production
  Moonraker control adapter maps only those operations to dedicated typed
  methods; it has no generic script method.
- The monitor caches some useful observations (`toolhead` position, homed axes,
  configured axis limits and active extruder; heater temperature and
  `can_extrude`; speed and extrusion factors). Most are untyped report data,
  not actuator admission evidence. It does not collect coordinate/extrusion
  modes, G-code origin, G-code position, live motion, current velocity or
  acceleration limits, configuration settings, endstop state, dual-carriage
  mode, or a queue-empty proof.
- Capability discovery proves loaded object names only. The current safety
  profile covers artifact dialect, nozzle, rectangular build volume, plate,
  and slicer profile; it does not bind kinematics, homing behavior, motion or
  extrusion limits, tools, transforms, sensors, or macro bodies.
- The shared per-printer gate serializes Klove work, not Mainsail, another
  Moonraker client, a local console, delayed G-code, or firmware behavior.
  Klove has no motion/extrusion journal, durable ambiguity fence, or operation-
  specific reconciler.

Sources for those facts are the [current operation
enum](../src/klove/domain/control.py), [production control

## Explicit unknowns and decision boundary

The audit leaves these questions deliberately unresolved for issue #19:

1. Whether any Moonraker/Klipper transport can provide a sufficiently narrow
   homing, jog, or extrusion effect without exposing generic G-code semantics.
2. Which kinematics, homing configurations, carriage/tool topologies, and
   sensor arrangements Klove could support conservatively.
3. How Klove can exclude or safely coexist with other Moonraker/G-code clients
   across the final proof-to-dispatch interval.
4. Which terminal observations can distinguish complete from partial physical
   effects, and which outcomes must require attended recovery permanently.
5. What hardware evidence and safety margins are sufficient for each supported
   printer profile. Names, models, near matches, and self-asserted configuration
   are not proof.

No shared document, code, transport, printer, or architecture decision is
changed by this audit.
